# p0-implementation.md — P0: безопасная оптимизация обработки соседних сущностей

> Фаза P0. Реализовано ограниченное изменение production-кода; результаты —
> в `p0-benchmarks.md`. Без Rayon, без изменений Tick Scheduler, `Game`,
> Pumpkin и Vanilla-поведения. Коммитов и push нет.

## 1. Пересмотр прежнего решения: кэширование отвергнуто

В `p0-decision.md` (фаза 2B) предлагалось кэшировать результат `others_near` один раз
на моба за тик. Это **не реализовано**, потому что гипотеза не подтвердилась ни кодом,
ни данными.

**Код.** Вызовы `others_near`/`nearby` в `mobs/**` используют *разные* области и
фильтры, поэтому «один скан на моба» не является переиспользованием идентичного запроса:

| Вызывающий | Область (AABB) | Фильтр |
|---|---|---|
| `ai::push_entities` | собственный `bounds` моба | `id≠me`, `alive`, `pushable`, пересечение |
| `goals` (look at mob), `goals.rs:~939` | `bounds.inflate(range, 3, range)` | `id≠me`, `alive`, вид |
| `brain::living_near` | `bounds.inflate(follow_range)` | `id≠me`, `alive` |
| `warden_brain` | `bounds.inflate(r)` | `alive` |
| `MobWorld::nearby` (цели, брачные партнёры, кошки у фантомов…) | куб `±(range+1)` | `alive`, расстояние, предикат, **сортировка по расстоянию** |
| `golem`, `enderman`, `aquatic`, `ravager` | свои малые области | свои предикаты |

Единый кэш потребовал бы запрашивать объединяющее надмножество областей (для
`follow_range` 16–35 блоков это куда больше кандидатов, чем нужно `push_entities`) и
затем фильтровать заново. Эквивалентность можно было бы доказать, но выигрыша нет:

**Данные (фаза 2B).** `near_calls/тик` ≈ `push_calls/тик` — коровы 2160 против 2110,
зомби 2906 против 2110: то есть **1,0–1,4 запроса соседей на моба за тик**, а не 2–3,
как предполагалось. Повторных запросов почти нет, экономить нечего. По условию задания
(§3C: «если требуется сложная инвалидация — не внедрять») кэш не внедрён.

## 2. Анализ текущей реализации (ответы на вопросы §2 задания)

1. **Повторные аллокации.**
   - `push_entities`: `Vec<(Who, Vec3)>::new()` на каждый вызов и рост через `push`. Для
     скопления из ≈2000 целей это ≈10 реаллокаций (ёмкость 4→8→…→2048) на вызов. **Это
     единственная заметная аллокация в измеренных сценариях → исправлено.**
   - `others_near`: один `Vec<u32>` на вызов; для кучи `extend_from_slice` выделяет один
     раз. Микробенчмарк: вся сборка кандидатов 1,35 мс/тик, буфер экономит 0,12 мс.
   - `MobWorld::nearby` (`Vec<&Seen>` + сортировка), `living_near`, `goals` (`candidates`)
     аллоцируют на вызов, но в измеренных сценариях редки (мало вызовов/тик).
2. **Повторная сортировка кандидатов.** `SeenGrid::candidates` вызывает
   `sort_unstable` на каждый запрос (`out.sort_unstable()`), чтобы вернуть индексы по
   возрастанию (порядок снимка). Она нужна: `grid.update` использует `swap_remove`
   (`seen_grid.rs`), который нарушает порядок внутри ячейки. На практике дёшево: в куче
   список ячейки уже упорядочен, `sort_unstable` (pdqsort) линеен на таких данных:
   2000 запросов × 2000 индексов = 1,35 мс/тик (≈0,3 нс на индекс). **Оптимизировать
   не нужно.**
3. **Безопасно ли переиспользовать буферы.** Для `targets` — да: thread-local
   `Cell<Vec>` с `take`/`set` (`Cell::take` оставляет пустой `Vec`; вложенный вызов,
   если бы он был, начал бы с пустого списка и ничего не сломал). Без `unsafe`, без
   мьютекса, без общей памяти. Для `near` в `others_near` — технически возможно, но
   результат — ленивый итератор, покидающий функцию, потому буфер пришлось бы вернуть
   через `Drop` собственного типа-итератора. Выигрыш ≈0,1 мс/тик не оправдывает смену
   возвращаемого типа → не сделано.
4. **Действительно идентичные запросы.** Нет (таблица в §1). Внутри `m.tick` данные
   неизменны (мир `w` держит `&snapshot` и `&grid`, обновление `grid.update` идёт *после*
   тика моба), но области и фильтры различаются.
5. **Как обновляется `SeenGrid`.** Сетка строится раз за тик по снимку
   (`SeenGrid::new`), затем после тика каждого моба вызывается
   `grid.update(i, bounds)` (`creatures.rs`): если колонка 4×4 блока сменилась, индекс
   удаляется из старой ячейки (`position` + `swap_remove`: O(размер ячейки)) и
   добавляется в новую. Мобы, тикающие позже, видят уже обновлённые боксы предыдущих —
   это Vanilla-семантика («ServerLevel ticks entities one after another»), и именно
   она делает невозможным наивное «заморозить снимок».
   *Наблюдение (не баг):* `candidates` возвращает `false` (вызывающий сканирует всех),
   если область охватывает больше колонок, чем в сетке непустых ячеек. В сетке из одной
   кучи это происходит почти на каждом запросе; в реальном мире ячеек много, и в
   измеренных прогонах `near_full_scans` ≈ 6 из ≈2000 запросов за тик.
6. **Оптимизации, сохраняющие точное множество и порядок.** Переиспользование буферов;
   пропуск прохода, который заведомо ничего не удаляет (сделано); компактный
   «структура массивов» (SoA) для проверки пересечений вместо чтения 360-байтной
   структуры `Seen` (не сделано, см. §8). Всё, что меняет *какие* сущности или в
   *каком* порядке взаимодействуют, — вне P0.

## 3. Что именно изменено

    static PUSH_TARGETS: std::cell::Cell<Vec<(Who, Vec3)>> =
        const { std::cell::Cell::new(Vec::new()) };
}
/// The longest list kept between calls; a bigger crowd frees its list.
const PUSH_TARGETS_KEPT: usize = 1 << 15;

fn push_entities(m: &mut Mob, w: &MobWorld, events: &mut Vec<MobEvent>) {
    ...
    let mut targets = PUSH_TARGETS.take();      // было: Vec::new()

    // pushable_by(None, None, true) == true всегда: при отсутствии команд проход пуст

    let crammed = targets.len() > 23;             // та же проверка, тот же draw
    ...

## 4. Почему это корректно

| Что | Почему поведение не меняется |
|---|---|
| Порядок и состав целей | Цикл сбора — прежний, в том же порядке снимка (`others_near` возвращает по возрастанию индекса, затем fallback-итерация по `others`). Буфер лишь очищается (`clear`) и заполняется тем же образом. `drain(..)` отдаёт элементы в порядке вставки. |
| Остаток буфера от прошлого вызова | `targets.clear()` сразу после `take()`; тест `a_reused_buffer_answers_as_a_fresh_one` показывает то же для `SeenGrid::candidates` (старый мусор в буфере не влияет). |
| Пропуск `retain` | `pushable_by(None, None, true)`: `own_rule = their_rule = Always`, `their_pushable = true`; первое условие ложно, а последнее выражение `own≠PushOtherTeams ∧ their≠PushOtherTeams ∨ same` истинно **независимо от `same`**. Условие входа `teams.player.is_some() \|\| !teams.mobs.is_empty()` не пропускает ни одного случая, где команда есть (тогда `retain` выполняется как раньше). Закреплено тестом `scoreboard::tests::without_teams_everything_is_pushable`, который также проверяет, что при наличии команд ответ зависит от правил. |
| Cramming и RNG | `crammed = targets.len() > 23` — тот же порог на том же множестве; `m.random.next_int_bound(4)` вызывается в том же месте при том же условии. Число и порядок draws не меняются. |
| Порядок событий | `events.push(MobEvent::Push {…})`, `m.velocity` — в прежнем порядке внутри того же цикла. |
| Прогрессивный снимок, отложенные блок-события, `apply_brain_events` | Не затронуты: P0 не трогает ни `snapshot`, ни `grid`, ни `creatures.rs`. |
| Память/потоки | thread-local, без `unsafe`; у каждого потока свой буфер (важно для будущего параллелизма: общей мутабельной памяти нет). Верхняя граница удерживаемой ёмкости `1<<15` элементов (≈1 МБ). |
| Паника внутри цикла | буфер потеряется (останется пустой `Vec`) и будет выделен заново: корректность не страдает. |

## 5. Добавленные тесты

`mobs/seen_grid.rs` (новые, обычные):
- `a_reused_buffer_answers_as_a_fresh_one` — повторное использование буфера: мусор в
  буфере, пустой ответ очищает, отказ сетки не оставляет «хвоста».
- `a_dense_pile_matches_the_scan` — плотная куча (400 боксов на одной точке) + соседи,
  широкий бокс, далёкие боксы; запросы разного размера, касание по грани (не
  пересечение), «весь мир» (отказ); сверка с полным перебором, порядок по возрастанию.
- `empty_grids_and_column_edges` — пустая сетка (отказывает, буфер пуст), боксы строго на
  границах колонок.
- `moving_boxes_are_found_where_they_are` — перемещение боксов между запросами
  (`grid.update`): между колонками, далеко, с расширением, обратно; после каждого шага
  ответ сетки совпадает с перебором; тест требует ≥100 содержательных ответов сетки.
- `buffer_reuse_cost` (`#[ignore]`) — микробенчмарк стоимости.

`scoreboard.rs`: `without_teams_everything_is_pushable` (условие пропуска `retain`).

Существующие тесты (`candidates_hold_every_meeting_box_in_order`,
`the_grid_finds_what_the_scan_finds` и остальные в `mobs::` и `scoreboard::`) проходят:
всего 101 passed, 0 failed, 7 ignored (микробенчмарки).

**Сравнение оптимизированной реализации с исходной на уровне игры** — через два
дифференциальных прогона (§6): для `push_entities` юнит-тест невозможен без
полного `MobWorld` (реестры, мир, коллизии), поэтому исходный бинарь сохранён и
сравнивается побитово.

**Ограничение покрытия, которое нужно знать:** в `mob_ai`-probe `teams` всегда пусты,
поэтому ветка «команды есть → `retain` выполняется» дифференциальным тестом не
проверяется. Она не менялась (тот же код под условием), а условие входа покрыто
юнит-тестом выше.

## 7. Результаты производительности (кратко; подробно в `p0-benchmarks.md`)

- Стационарные сценарии (`cows_*`), нагрузка идентична: `mob_tick` −26 / −33 / −36 / −27 %,
  MSPT avg −12 / −24 / −30 / −11 % (500 / 1000 / 2000 / 4×500 коров), все вне шума.
- Зомби и смесь (нестационарные; нормировано на число кандидатов): −20 % и −10 % на кандидата.
- Хвосты p95/p99: улучшение **не заявляется**; у `mixed` в A/B p99 вырос с 91 до 183 мс
  в трёх повторениях, но прямой подсчёт медленных тиков на одном окне регрессии не
  показал (после P0: 3 и 1 тик >100 мс против 10 и 1 до). Вероятная причина — смещение стенных окон (разная скорость тиков); прямо не доказано.
- Выровненный по тикам замер `/tick sprint 2100` для `mixed` (`p0-benchmarks.md` §3.2):
  53,1 ± 6,1 → 46,1 ± 4,6 мс/тик (−13 %, в пределах шума), медленных тиков >100 мс
  [50, 30, 1] → [1, 1, 1]. Регрессии хвоста нет; улучшение хвоста не заявляется.

## 8. Что изменилось в сложности и какие узкие места остались

**Сложность не изменилась.** Число просмотренных кандидатов за тик прежнее
(`cows_2000`: 4 017 200 → 4 016 824). Работа по-прежнему O(Σk²) по скоплениям — это
свойство Vanilla-семантики (в Java `getEntities` тоже O(k) на сущность), а не дефект
реализации. P0 снизил **константу**: с ≈9,3 до ≈6,0 нс на кандидата на `cows_2000`.

Оставшиеся узкие места (по разбивке до P0 на `cows_2000`, 37,9 мс в `push_entities`):
1. **Цикл по кандидатам** — ≈21–23 мс: обход ≈2000 `Seen` на моба. `Seen` — **360 байт**
   (замер `lookup_cost`), поля `id/alive/pushable/bounds` лежат в разных кэш-линиях, то
   есть каждый кандидат стоит нескольких обращений в память. Следующий точный (без
   изменения семантики) шаг — компактный массив (SoA) `{id, alive&pushable, bounds}`,
   построенный вместе со снимком и обновляемый `grid.update`. Оценка выигрыша без
   прототипа невозможна.
2. **Применение толчков** — ≈6,5 мс: 4 млн пар → события `Push`, `PendingPushes`
   (хэш-карта списков), `apply_mob_pushes`.
3. **Сам O(k²)**: пока Vanilla-семантика требует «каждый с каждым» в куче, потолок
   алгоритмики — константа.
4. **Хвосты** активного AI (зомби: p99 ≈ 0,8 с в A/B) — не связаны с P0, обусловлены
   эволюцией толпы; требуют отдельного исследования.
5. **Сценарий-артефакт:** в `cows_*` все коровы стартуют в одной точке (мёртвая зона
   `dd < 0.01` Vanilla — они не расталкиваются). Реальные фермы чаще смещены; на таких
   `offset_*`-сценариях корректность проверена, производительность — нет (в A/B их нет).

## 9. Регрессии

- **Не найдено** в корректности (см. §6) и в средних (улучшение во всех шести
  сценариях).
- **Аномалия методики:** `mixed` p99 (см. §7). Не подтверждена прямым подсчётом.
- **Память:** до ≈1 МБ постоянно на поток (на практике ≈64 КБ при 2000 сущностей).
- **Git:** предупреждения `LF will be replaced by CRLF` при `git diff` — особенность
  `core.autocrlf` на этой машине; `rustfmt` пишет LF, CI на Linux их не увидит.

## 10. Влияние на дальнейшее распараллеливание

- P0 удешевил последовательную часть, которую P1 будет делить. По закону Амдала это
  *снижает* абсолютный выигрыш параллелизма, но улучшает итоговый MSPT и, что важнее,
  **не добавляет общего мутабельного состояния**: буфер thread-local, у каждого рабочего
  потока будет свой.
- Профиль после P0 не изменил главного вывода 2B: в толпе всё сосредоточено в одном
  скоплении, то есть в **одном острове взаимодействия**. Параллелизм между островами не
  ускорит одну кучу; выгоден лишь для мира с несколькими удалёнными скоплениями
  (типичный сервер с игроками в разных местах).
- Параллелизм *внутри* острова (обработка целей одного моба параллельно) нарушает
  Vanilla-семантику «мобы тикают по очереди, следующий видит предыдущего уже
  обновлённым» (`snapshot[i]`/`grid.update` после каждого тика): для точного результата
  нужна последовательная цепочка. Это определяет форму P1.

## 11. P1: предлагаемый эксперимент с настоящим параллельным выполнением

> Не реализуется в этом задании. Это план эксперимента с критериями успеха и отказа.

### 11.1 Гипотеза и формулировка

**H1.** В реалистичных нагрузках сущности распадаются на независимые *острова
взаимодействия* настолько, что тик островов, не использующих общий RNG, можно выполнять
параллельно на нескольких ядрах с **побитово тем же** результатом, что и
последовательный, и ускорением `mob_tick`, близким к `min(ядра, число островов)` с
учётом Амдала.

Это не «Entity Islands как таковые»: сначала проверяется, *существует ли* достаточная
независимость, затем — можно ли её исполнить параллельно без потери точности.

### 11.2 Зависимости, найденные в коде `tick_creature_entities` (определяют острова)

| Зависимость между мобами | Где | Следствие для острова |
|---|---|---|
| Прогрессивный снимок: моб *i* видит мобов *j<i* уже обновлёнными, *j>i* — в начале тика (`snapshot[i]`, `grid.update` после тика) | `creatures.rs` | мобы, которые могут *читать* друг друга, обязаны быть в одном острове и тикаться в порядке списка |
| Чтение любых мобов в радиусе поведений: `push_entities` (бокс), `nearby` (до 16+), `living_near`/цели (до `follow_range` ≈ 16–35), LoS (до 128) | `mobs/**` | радиус связи R = максимум радиусов чтения (требует аудита) |
| Чтение по идентификатору: `seen(id)`/`target_info(Who::Mob(id))` — цель, партнёр, поводок, всадник, дом/кровать жителя, караван | `world.rs`, `ai.target` | нужны *явные рёбра по id* (как `links` у Pumpkin), а не только расстояние |
| Толчки «действуют сразу» (`PendingPushes`): моб *i* меняет скорость моба *j>i* до его тика | `mobs.rs` | толчки не пересекают границу острова, если R ≥ радиуса бокса |
| `apply_brain_events(&mut mobs, …)` пишет в **других** мобов сразу после тика текущего | `mobs.rs` | партнёр по размножению и т. п. — рёбра по id |
| Общий RNG уровня `scratch` (`world.random.clone()`), передаваемый в `Mob::tick` | `creatures.rs`, `mobs/ai.rs` | по `level_random` в `ai.rs` его получают только мозги и часть видов (`monster_brain` — breeze/creaking, `villager_brain`, `warden`, `animal_brain` — sniffer/axolotl и др., `copper_golem::update_weathering`, `bee::tick`); остальные виды его не трогают (**полный список требует аудита в P1a**). Любой остров с таким мобом — «RNG-связанный»: все RNG-связанные острова должны идти последовательно в порядке списка |
| Общий `events: Vec<MobEvent>` в порядке тиков | `creatures.rs` | события островов собираются отдельно и сливаются **по исходному индексу моба** (стабильно) — воспроизводит последовательный порядок |
| `died`/`dead`/`keep`/`bindings` (LAN) | `creatures.rs` | то же слияние по индексу |

### 11.3 Этапы (каждый с воротами точности)

**P1a — измерение без потоков (самый дешёвый, решающий).**
1. Построить разбиение на острова из снимка: рёбра = расстояние ≤ R (консервативный R,
   например `max(follow_range, 16) + запас`) ∪ рёбра по id (цель, поводок, всадник,
   партнёр, дом/кровать, караван) ∪ метка «RNG-связанный».
2. Логировать на каждый тик: число островов, размер наибольшего, доля `mob_tick`
   в наибольшем острове (верхняя граница ускорения по Амдалу), доля RNG-связанных.
3. **Доказательство независимости без потоков:** выполнить тот же тик, но мобы
   переупорядочены *по островам* (острова подряд, внутри — исходный порядок), и
   сравнить результат побитово (ворота: дифференциальный прогон `mob_ai`-probe и
   плотных сценариев, SHA-256 совпадает). Если переупорядочивание меняет результат —
   независимость не доказана, и это найдёт пробел в аудите радиуса *до* появления
   гонок.
4. Отладочная проверка границ (как `entity_islands::enter/leave` в Pumpkin): в debug-
   и тестовых сборках чтение записи снимка, не принадлежащей острову текущего моба,
   — паника. Это эмпирически проверяет аудит R.

**P1b — исполнение независимых островов на потоках.**
1. Мобы острова временно переносятся в `Vec<Mob>` острова (без `unsafe`: владение
   отдельными `Vec` вместо `&mut` на пересекающиеся срезы), после тика возвращаются в
   исходный порядок.
2. У каждого острова свои `events`, `PendingPushes`, `died/dead/keep`, **своё
   наложение на снимок/сетку** (общий read-only снимок начала тика + локальные
   обновления своих мобов). Межостровные чтения запрещены конструкцией (см. P1a.4).
3. RNG-связанные острова выполняются последовательно в порядке списка; нет RNG-
   связанных — параллельно. Пул потоков создаётся один раз вне тика; число потоков
   настраиваемо; Rayon допустим только здесь и только за флагом/переменной окружения,
   по умолчанию выключен (однопоточный путь сохраняется).
4. Слияние результатов в исходном порядке мобов.

**P1c — масштабирование.** Сценарии: `cows_spread` (4 острова), новый `herds_32x60`
(32 стада по 60 коров, разнесённые на ≥300 блоков), `village` (RNG-связанные жители —
проверка последовательного отката), `mixed_spread`, плюс единая куча (контроль: ожидаем
≈1,0×). Ядра: 1, 2, 4, 6, 12. Измерять `mob_tick`, MSPT, затраты на построение
островов, на слияние и пусковые затраты потоков.

### 11.4 Ворота точности (обязательны на каждом этапе)

1. Побитовое совпадение сырого вывода `mob_ai`-probe (22,5 МБ) и плотных сценариев (17 +
   36 МБ) с последовательным эталоном — **для каждого числа потоков (1…12) и ≥ 20
   повторных запусков** (детерминизм при гонках потоков).
2. Vanilla-parity `mob_ai` не хуже 139/141.
3. Новые сценарии probe с несколькими удалёнными стадами и с RNG-связанными мобами
   (жители, ворден) — тоже побитово.
4. Сохранение порядка RNG: сравнение числа/порядка draws (в выводе probe это поле `rng`).

### 11.5 Методика замеров (исправление выявленной в P0 проблемы)

Для P1 **обязательно** окно, выровненное по игровому тику: `/tick sprint N` после
общего прогрева (Horizon его поддерживает и печатает «ms per tick»), а не стенные
30 с. В P0 именно разная скорость тиков смещала окна между группами и сделала
хвостовые метрики несопоставимыми. Хвосты считать числом тиков > порога на одном и том же
диапазоне тиков. Минимум 3 независимых запуска, чередование ABBA, критерий шума
заранее.

### 11.6 Критерии успеха и отказа

**Успех:** ворота точности пройдены; на `herds_32x60` на 6 ядрах `mob_tick` ≥ 3,0×
быстрее одно­поточного; на единой куче нет регресса (> −3 %); накладные расходы
построения островов ≤ 5 % `mob_tick`.

**Отказ (остановить P1b/c):** если на P1a наибольший остров в типичных нагрузках
(`village`, `mixed_spread`, спаун-сценарий с несколькими игроками) занимает > 60 % работы
`mob_tick` — по Амдалу потолок < 1,6× на 6 ядрах, и затраты на построение островов не
окупаются; либо если переупорядочивание по островам (P1a.3) хотя бы раз меняет
результат и причину не удаётся устранить аудитом радиуса.

### 11.7 Риски

| Риск | Митигация |
|---|---|
| Неполный аудит радиусов чтения → тихий рассинхрон | P1a.3 (доказательство без потоков) + debug-проверка границ P1a.4 |
| Скрытые побочные эффекты `Mob::tick` (мод-хуки, звуки, `needs_sync`) | всё через `events` с слиянием по индексу; моды WASM (`tick_mods`) вне цикла |
| LAN-гости (`guest_events`, `bindings`) | острова с привязанными к гостю мобами — последовательные (как RNG-связанные) в первой версии |
| Стоимость построения островов каждый тик | адаптивное расписание: планировать только при ≥ N мобов и когда прошлый план был выгоден (идея Pumpkin, код не копируется — GPLv3 против MIT) |
| Потоки не окупаются на малых нагрузках | порог включения по числу мобов; на пустом мире тик 0,26 мс — любой оверхед виден |
