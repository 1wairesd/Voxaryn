# p1-parallel-architecture.md — Архитектура параллельного тика мобов (P1)

> Фаза P1. Первый прототип настоящего многоядерного выполнения части симуляции.
> Всё за экспериментальным cargo-feature `parallel-entities` (по умолчанию
> выключен) и переменной окружения `HORIZON_ENTITY_THREADS` (по умолчанию 0).
> Без них бинарник выполняет ровно тот же код, что после P0. Измерения —
> в [p1-benchmarks.md](p1-benchmarks.md), проверки — в [p1-correctness.md](p1-correctness.md).
> Код Pumpkin (GPLv3) не копировался: прочитана только идея `entity_islands.rs`
> (острова сущностей + rayon); реализация и модель зависимостей свои.

## 1. Что именно распараллелено

Распараллелен **проход мобов** `tick_creature_entities` (`game/creatures.rs`):
полный тик каждого моба (`Mob::tick`: AI, цели, навигация и поиск пути, физика,
толкание, урон от среды, события) — это 76–90 % MSPT в сценариях с толпами
(Phase 2B). Единица параллелизма — **остров**: группа мобов, про которую
доказано, что за этот тик она не может ни прочитать, ни изменить мобов из
другого острова. Остров тикает целиком на одном потоке, мобы внутри — строго
в исходном порядке, как в ванилле (`ServerLevel` тикает сущности по списку).

Не распараллелено (и не трогалось): смерти и дропы после прохода, снаряды,
спавн, блоки, редстоун, чанки, игроки, LAN/трекинг. Всё это остаётся на главном
потоке сервера до и после прохода.

## 2. Поток данных одного тика

```
tick_creature_entities
 ├─ snapshot = seen(mob) для всех мобов             (как раньше)
 ├─ try_pass(input, out)            ── только с feature и THREADS>0
 │   ├─ gate: можно ли вообще?       → нет: fallback(reason), ничего не тронуто
 │   ├─ plan: острова (union-find)   → < 2 островов: fallback("one-island")
 │   ├─ [verify] эталон: mob_pass по клонам, последовательно
 │   ├─ split: раздать каждому острову СВОИ копии состояния
 │   ├─ run: rayon pool.install → par_iter_mut, крупнейший остров первым
 │   │        каждый остров: mob_pass(свои мобы, свой snapshot, ...)
 │   ├─ merge: сборка в ИСХОДНОМ порядке мобов по Mark
 │   └─ [verify] сравнение с эталоном → при отличии берётся эталон
 └─ иначе: mob_pass(input, out, None)  ── ровно прежний цикл
```

### 2.1 Одна реализация семантики

Тело прежнего цикла перенесено **дословно** в `fn mob_pass` (`game/creatures.rs`).
Последовательный путь вызывает его один раз на все мобы, параллельный — по
разу на остров. Дублирования логики нет, поэтому параллельный путь не может
«разойтись» с последовательным из-за правки только в одном месте.

- `PassInput` — то, что все мобы читают одинаково: `MobWorld` (блоки, игрок,
  команды, правила), игроки уровня, виды LAN-гостей, `ticking(x,z)`, UUID.
  Только `&` — разделяется между потоками без копий (`MobWorld: Sync`).
- `PassOut` — всё, что проход пишет: мобы, снапшот (он обновляется по ходу
  прохода — «каждый следующий видит предыдущих уже сдвинутыми»), множество
  умерших, привязки гостей, scratch-копия level random, события, мёртвые,
  события гостей.
- `Mark` — где после тика *i*-го моба кончаются его записи в событиях,
  событиях гостей и списке мёртвых, и остался ли он жив. Нужен только для
  слияния.

### 2.2 План островов (`mobs/islands.rs`)

Чистая функция `plan(snapshot, radius) -> Plan`, без доступа к игре:

1. **Радиус досягаемости** `R = max(follow_range по всем мобам, 16) + REACH_MARGIN (11)`.
   Запас 11 = полуширины двух хитбоксов + `inflate` + перемещение двух мобов
   навстречу за тик. Для коров R = 27, для зомби R = 46.
2. Мобы раскладываются по **столбцам XZ** размера R; все мобы столбца — в один
   остров; каждый столбец объединяется с 8 соседями. Два моба на расстоянии
   ≤ R всегда в соседних столбцах, значит всегда в одном острове (это свойство
   проверяет тест `mobs_within_reach_always_share_an_island` на 200 случайных
   конфигурациях). Высота не учитывается — консервативно.
3. **Связи по id** на любом расстоянии: `Seen.target` и `Seen.hurt_by` моба
   объединяют его с целью и обидчиком.
4. Детерминированность: корни union-find — минимальный индекс, острова
   упорядочены по первому индексу (тест `the_plan_is_deterministic`).

Ошибка плана в сторону «слишком крупно» стоит только параллелизма; в сторону
«слишком мелко» — корректности. Модель выбрана так, чтобы возможна была
только первая.

### 2.3 Gate: когда весь тик идёт последовательно

`gate()` в `game/creatures_parallel.rs` отказывает (весь тик через `mob_pass`)
при любом из условий:

| Причина (`fallbacks`) | Условие | Почему |
|---|---|---|
| `disabled` | ранее остров тронул level random | страховка, см. §3 |
| `rng-trace` | собран с feature `rng-trace` | трасса RNG пишется в порядке выполнения |
| `few` | мобов < `HORIZON_ENTITY_MIN_MOBS` (64) | накладные расходы больше выигрыша |
| `state` | snapshot/списки событий не в исходном состоянии | нарушен инвариант входа |
| `species` | хотя бы один **тикающий** моб непроверенного вида | его чтения других мобов не ограничены (см. §4) |
| `links` | наездник, маунт, поводок (в т.ч. отложенный) | связи между сущностями вне модели островов |
| `duplicate-ids` | повтор id | слияние по id было бы неоднозначным |
| `one-island` | план дал < 2 островов | параллелить нечего |
| `dominant` | один остров содержит ≥ 75 % **тикающих** мобов | выигрыш прохода < 1.33×, а split/merge стоят ~1 мс на 2000 мобов. Добавлено по результатам замеров: без этого `cows_spread` (1 тикающая область + 3 вне зоны симуляции) и `cows_2000` (одна толпа + 3 моба рядом) шли параллельно и теряли до 1.8 мс/тик (см. p1-benchmarks §4) |

Все проверки gate — только чтение; отказ ничего не меняет, и тик идёт
ровно путём P0.

Моб вне entity-ticking чанков проверяет только деспавн (читает себя и ближайшего
игрока), поэтому его вид не блокирует тик.

### 2.4 Проверенные виды

`islands::verified()`: **Cow, Mooshroom, Pig, Sheep, Chicken, Zombie.** Для каждого
проведён аудит всех чтений других мобов за тик:

- толкание (`push_entities`) и `others_near` — ограничены хитбоксом + 1;
- `nearby` и цели (`NearestAttackableTarget`, `TemptGoal`, `FollowParent`,
  `Breed`) — ограничены `follow_range`;
- тревога HurtByTarget у зомби (`alert others`) перебирает `w.others`, но с
  фильтром по дистанции ≤ follow_range; сами `SetTarget` применяются после
  цикла (у мобов текущего острова, т.к. все они в радиусе);
- ни один из этих видов не берёт из **level random** (только из собственного
  `Mob.random`).

Исключены: жители, рейдеры, иллагеры (глобальные сканы `w.others` без
ограничения дистанции, брейны с level random), ламы (караван по id без
ограничения), вексы (владелец по id), скелеты и пауки (не проаудированы в P1).

### 2.5 Пул потоков

- `rayon = "=1.12.0"` (optional, только под feature); один постоянный
  `ThreadPool` на процесс, `HORIZON_ENTITY_THREADS` потоков `horizon-entity-{i}`.
  Ни одного OS-потока на остров или на тик.
- `par_iter_mut().with_max_len(1)` — каждый остров отдельная задача; острова
  отсортированы по убыванию размера (крупнейший — критический путь — стартует
  первым). `HORIZON_ENTITY_ORDER=smallest|shuffle:N` меняет порядок для тестов.
- `THREADS=1` — параллельный путь на одном работнике: измеряет чистые
  накладные расходы split/merge без выигрыша.
- Главный поток сервера ждёт внутри `pool.install` (не берёт работу сам).

### 2.6 Владение данными: что пришлось изменить

| Изменение | Зачем |
|---|---|
| `pub trait Goal: Debug + Send` (`mobs/goals.rs`) | `Mob` хранит `Box<dyn Goal>`; без `Send` моба нельзя передать работнику. Все реализации уже были `Send` — добавление прошло без правок целей |
| `stats::add(PathStats)` (`mobs/path.rs`) | thread-local счётчики поиска пути работников возвращаются в главный поток |
| `mob_pass`, `PassInput`, `PassOut`, `Mark` | вынесение тела цикла (см. §2.1) |

Не добавлено ни одного `Arc`, `Mutex`, атомика или `RefCell` в структуры
мобов/мира; нет глобального мьютекса вокруг `Game`. Острова не разделяют
ничего изменяемого: каждый получает **свои** `Vec<Mob>`, `Vec<Seen>` (и свою
сетку `SeenGrid`, свой индекс id, свои `PendingPushes` — их строит `mob_pass`),
копию `died`/`bindings` по своим id, клон level random, пустые списки событий.
Общее — только `&PassInput`. Поэтому результат не может зависеть от
планирования потоков — это проверяется, а не только утверждается (§3).

Thread-local буфер `PUSH_TARGETS` из P0 (`Cell<Vec>`, take/set) безопасен на
работниках: у каждого потока свой экземпляр; повторный вход получает пустой
`Vec` (take оставляет пустой) и только теряет повторное использование буфера.

### 2.7 Слияние

Для каждого исходного индекса известен (остров, локальный индекс). Обход в
исходном порядке мобов: из «дренажа» острова забираются ровно записи этого
моба (события, события гостей, мёртвые — до его `Mark`), сам моб — если
`kept`. Так итоговые списки побайтно те же, что дал бы последовательный проход
(у которого события моба *i* идут после событий мобов < *i*). `died` и
`bindings` переносятся по id острова (моб трогает только свой id). Отложенные
толчки применяются внутри острова в конце его прохода, как в `mob_pass`.

## 3. Страховочные сетки

1. **Level random.** После прогона у каждого острова сравнивается digest его
   копии level random с исходным. Если какой-то остров из него брал — флаг
   `DISABLED`, ошибка в лог, до конца процесса только последовательный путь
   (текущий тик уже слит; при включённом verify он заменяется эталоном).
2. **`HORIZON_ENTITY_VERIFY=N`.** Каждый N-й параллельный проход (1 = каждый)
   сначала выполняет последовательный `mob_pass` по клонам (эталон), после
   слияния сравнивает: Debug-хеш каждого моба (всё состояние: позиция,
   скорость, здоровье, цели, память, путь, RNG моба…), событий, событий
   гостей, мёртвых, отсортированные `died`/`bindings`, level random. При
   любом отличии — лог с первым различием и **берётся эталон**.
3. Детерминированный план + слияние по исходному порядку + отсутствие общего
   изменяемого = независимость от расписания; проверено разными порядками
   (`largest`, `smallest`, `shuffle:7`) и числом работников 1…12.

## 4. Почему плотная толпа — один остров

В `cows_2000`/`zombies_2000`/`mixed` все мобы стоят в пределах нескольких
блоков: любые два соседа в радиусе толкания, цепочки «каждый трогает
соседа» связывают всю толпу. **Это не консерватизм модели, а настоящая
зависимость:** моб *k* толкает соседа и сам сдвигается, моб *k+1* видит
уже сдвинутого. Разрезать такую толпу без смены семантики нельзя; по
требованию задачи мы этого не делаем (`fallback: one-island`).

### 4.1 Можно ли параллелить вычисления *внутри* острова

Оценено, не реализовано:

| Кандидат | Независим? | Вывод |
|---|---|---|
| сбор кандидатов-соседей (`others_near`) заранее, read-only | нет: snapshot прогрессивный — моб *k* должен видеть позиции мобов < *k* **после** их тика | заранее можно только надмножество кандидатов; проверка пересечения всё равно последовательна. По P0 это 1.0–1.4 запроса на моба по разным AABB — выигрыш мал |
| поиск пути | частично (читает блоки, не мобов) | Phase 2A: ≤ 2 % MSPT — потолок выигрыша ниже стоимости синхронизации |
| `GoalSelector.canUse` целей, не читающих мобов (RandomStroll, LookAround) | да, но берут `Mob.random` в порядке тика моба | их стоимость мала; сложность (разделить фазу целей и фазу движения) — это перестройка `Mob::tick` |
| физика/коллизии с блоками | да по блокам, нет по мобам (толкание) | разделение «движение по блокам ∥ → толкание последовательно» меняет порядок операций внутри `Mob::tick` (ванилла: move → push) — нужна доказанная эквивалентность |

Итог: внутри плотного острова безопасного дешёвого параллелизма нет; потолок —
одноядерная скорость прохода (её P0 уже снизил на 26–36 %).

## 5. Что нужно для P2

1. **Больше проаудированных видов** (скелеты, пауки, криперы — частые в
   реальных мирах) и **поострово-последовательная полоса** для
   непроверенных: сейчас один житель где угодно в тикающей зоне выключает
   параллелизм на весь тик. P2: такие мобы и всё в их (расширенном) радиусе —
   в один «последовательный» остров, выполняемый на главном потоке в своей
   позиции порядка.
2. **Level random по островам**: брейны жителей/пиглинов берут из общего
   level random — порядок их вызовов меняет мир. Нужна либо доказанная
   изоляция (только один остров с потребителями level random), либо
   ванильный порядок через отдельную полосу (п.1).
3. **Связи сущностей** (наездники, поводки, караваны) — в план как явные рёбра,
   а не как отказ всего тика.
4. **Точнее план**: столбцы размера R с объединением 8 соседей сливают острова
   до ~2R; проверка реальной дистанции между занятыми столбцами (или ячейки
   R/2 с соседями ±2) дала бы больше островов при плотной сетке ферм (см.
   `herds_16x125` в p1-benchmarks).
5. **Спавн во время тика / генерация**: новые мобы из генерации могут быть
   непроверенных видов — нужен gate по островам, а не по тику.
6. **Дешевле split/merge**: сейчас ~1.3 мс/тик на 2000 мобов на главном
   потоке (раздача `Vec<Mob>`/`Vec<Seen>` по островам, клоны level random,
   сборка в исходном порядке). Хранение мобов сразу по островам между тиками
   и параллельное построение снапшота убрали бы большую часть.
7. **Раздувание работы на многих ядрах** (сумма времён островов ×1.75 на 6
   потоках) — профилировать; кандидаты: частота, L3, системный аллокатор
   Windows (в игре нет `#[global_allocator]`).
8. Параллелизм *других* фаз (блоки, редстоун) — отдельная модель зависимостей,
   в P1 не рассматривалась.
