# parallel-candidates.md — Первая подсистема для распараллеливания

> Фаза 1.5, задача 6. Выбор опирается на **реальные измерения**
> (`profiling-results.md`), разбор зависимостей тел функций (`tick-architecture.md`
> §9–§12) и анализ Pumpkin (`pumpkin-analysis.md`). P0 здесь **не реализуется**.

## 1. Исходные данные для выбора

Из `profiling-results.md` (i5-12400F, release, сервер без игроков):
- При 1600–2000 сущностях **`tick_mobs` ≈ 60% тика** (1.08–1.26 мс из 1.8–2.1 мс),
  срабатывает почти каждый тик (1224–1225 сэмплов за ~1200 тиков).
- Блок-фазы, блок-сущности, предметы на тех же сценариях остаются < 0.5 мс.
- Redstone-сценарий недооценён (статическое поле), стоимость блок-тиков не измерена.

Из `tick-architecture.md` §9–§12:
- Сущностная фаза (`tick_creature_entities`) сериализована общим `world.random` и
  пошагово обновляемым `snapshot` (моб N+1 видит моба N обновлённым).
- **Pathfinding (`Finder::find`, A*) — единственная крупная read-only по миру часть**:
  читает мир через `MobWorld`, возвращает owned `Path`, не мутирует мир.

## 2. Кандидаты, ранжированные по (выигрыш × безопасность ÷ стоимость)

### Кандидат №1 — Параллельная предподготовка pathfinding ✅ ВЫБРАН
Вынести **расчёт путей A*** для мобов, которым в этом тике нужен новый путь, в
`rayon::par_iter` по read-снимку мира; готовые `Path` применить последовательно в
исходном порядке внутри `tick_creature_entities`.

- **Выигрыш:** высокий внутри доминирующей фазы. Pathfinding — самая тяжёлая
  вычислительная часть тика мобов (A* с кучей, сканирование блоков/коллизий).
- **Стоимость синхронизации:** низкая. Fork-join на границе под-шага; вход —
  read-only `MobWorld`-снимок, выход — `Vec<Option<Path>>`. Нет разделяемых локов.
- **Сложность:** низкая-средняя. Не трогает модель владения `Game`; не меняет
  хранение сущностей (в отличие от entity-islands Pumpkin). Нужно вычленить точку,
  где моб запрашивает путь, и сделать её двухфазной (собрать запросы → посчитать
  параллельно → раздать).
- **Риск порядка событий:** низкий. Путь не меняет мир и не трогает RNG; применяется
  детерминированно. Движение по пути и побочные эффекты остаются в последовательном
  `m.tick`.
- **Детерминизм:** сохраняется, **если** (а) A* не тянет из общего `world.random`
  (проверить: `find` принимает позиции и параметры, RNG в сам поиск не входит — в
  vanilla `PathNavigation` детерминирован по состоянию мира), и (б) снимок мира для
  всех задач — один и тот же (срез до под-шага).
- **Совместимость:** высокая. Аддитивно, за feature-флагом; однопоточный путь
  сохраняется.
- **Тестирование:** `mob_ai` parity-харнесс (probe `examples/mob_ai_probe.rs`);
  сверка, что путь каждого моба побитово совпадает с последовательным расчётом;
  детерминизм-прогон (см. `benchmark-plan.md` §5). Замер доли `tick_mobs` до/после.

### Кандидат №2 — Параллельный расчёт «намерений» AI (brain/goals) по снимку
Считать параллельно решения мозга/целей (выбор цели, следующего действия) по
read-снимку, применять последовательно.
- Выигрыш средний; **риск выше** — многие brain-поведения тянут общий RNG и читают
  обновляемый `snapshot`, т. е. зависят от порядка. Границу «чистой» части провести
  труднее, чем у pathfinding. Откладывается до P1.

### Кандидат №3 — Параллельные блок/random-тики по чанкам (как Pumpkin `par_chunks`)
`tick_blocks` → `tick_chunk_random` по непересекающимся чанкам.
- Потенциально высокий выигрыш, **но не подтверждён измерением** (блок-фазы < 0.5 мс
  в наших сценариях; redstone-сценарий недооценён). Риск порядка высок на границах
  чанков (redstone-каскады, `level_events`-очередь строго упорядочена). Требует
  отдельного замера с реальным осциллятором. Откладывается.

### Кандидат №4 — Параллельный тик сущностей через reach-острова (полный подход Pumpkin)
- Максимальный выигрыш, **максимальный риск и стоимость**: требует перевода хранения
  сущностей на разделяемое/атомарное состояние (`Arc`+атомики у Pumpkin) и reach-аудита.
  Это целевая архитектура, но не первый шаг (нарушает «не переписывать тик»). Остаётся
  долгосрочной целью (регионы/домены из `pumpkin-scheduler`).

## 3. Выбор: Кандидат №1 (параллельный pathfinding) как P0

**Почему именно он — по измерениям и зависимостям:**
1. Бьёт в измеренную доминирующую фазу (`tick_mobs` ≈ 60%).
2. Единственная крупная **read-only по миру** часть тика (подтверждено телом `Finder`)
   — минимальный риск для порядка событий и детерминизма.
3. Не меняет модель владения `Game` и хранение сущностей — соблюдает ограничение
   «не переписывать тик, сохранять однопоточную реализацию».
4. Даёт переиспользуемый паттерн fork-join (снимок → `par_iter` → упорядоченное
   применение) для будущих кандидатов 2–4.

**Проверяемая гипотеза P0:**
> Расчёт путей A* для мобов, которым нужен новый путь, можно вынести в параллель по
> неизменяемому снимку мира и применить детерминированно, сократив долю `tick_mobs`
> на многосущностной нагрузке **без** изменения результата симуляции.

## 4. Предусловия, которые надо проверить ДО реализации P0

1. **RNG в pathfinding.** Убедиться, что `Finder::find` и путь к нему не тянут из
   `world.random` (иначе параллельный порядок сломает детерминизм). По сигнатуре
   `find(positions, max_path_length, reach_range, max_visited)` RNG не передаётся —
   но проверить вызывающий код (как часто и когда моб решает перестроить путь).
2. **Снимок мира.** Pathfinding читает блоки/коллизии через `MobWorld`. Нужно, чтобы
   все параллельные задачи читали один срез мира (до любых мутаций под-шага) — иначе
   результат зависит от гонки. `MobWorld` уже read-view; подтвердить, что он `Send+Sync`
   или легко делается таким для среза.
3. **Частота перестройки пути.** Если путь перестраивается редко (раз в N тиков на
   моба), выигрыш меньше ожидаемого — замерить долю именно A* внутри `tick_mobs`
   (сейчас спаны этого не разделяют; нужна временная инструментализация под-шага).
4. **Порог включения.** Как `MIN_PARALLEL_ENTITIES` у Pumpkin — не распараллеливать,
   когда мобов мало (fork-join не должен добавлять оверхед на пустом мире; у нас
   пустой мир 0.26 мс — любой оверхед заметен относительно).

## 5. Стоимость синхронизации (оценка, не измерено)

- **Вход параллельной части:** срез `MobWorld` (read-only) + список запросов пути.
  Клонирование снимка — цена, которую надо измерить; возможно, достаточно `&`-ссылки
  на неизменяемый мир на время под-шага.
- **Выход:** `Vec<Option<Path>>` по индексу моба — применяется последовательно.
- **Нет разделяемых локов** в параллельной части (ключевое преимущество над entity-islands:
  там нужно атомарное состояние сущностей).
- На Windows **нельзя** измерить CPU-vs-wall (`thread_cpu()` = None) → стоимость
  синхронизации мерить по росту суммарного wall при малой нагрузке и по профайлеру
  (ETW) либо на Linux/macOS.

## 6. Критерии успеха P0 (уточнены измерениями)

1. **Корректность:** путь каждого моба и итоговое состояние сущностей совпадают с
   однопоточным эталоном на фиксированном сценарии (seed 12345); `mob_ai` parity
   зелёный (где доступен runner — на Windows только прямой probe, не `parity.py`).
2. **Выигрыш:** доля `tick_mobs` на сценарии «dense_entities» (2000 сущностей)
   сокращается измеримо на ≥ 4 используемых ядрах относительно baseline 1.26 мс.
   Заявлять только измеренное через `.local/tick_bench.py`.
3. **Нет регресса:** на пустом мире (baseline 0.26 мс MSPT) тик не растёт при
   выключенном или «пустом» параллелизме (порог включения).
4. **Изоляция:** за feature-флагом, по умолчанию выключен; `fmt`/`clippy -D warnings`/
   тесты `horizon-world`,`horizon-core` зелёные.
5. **Детерминизм:** два прогона фиксированного сценария дают идентичный результат
   (NBT + порядок событий, см. `benchmark-plan.md` §5 и профиль корректности ниже).

## 7. Связь с проверкой корректности

Метод сравнения «однопоток vs будущий параллелизм» описан в `benchmark-plan.md` §5 и
развит в `baseline.md`. Для P0 (pathfinding) строгое совпадение требуется для: путей
мобов, позиций/скоростей сущностей после тика, последовательности `world.random`
(число и порядок draws), очереди `level_events`. Нормализованное сравнение допустимо
только там, где vanilla сам недетерминирован по порядку (например, итерация по
不упорядоченным коллекциям) — таких мест в выбранной подсистеме быть не должно, т. к.
pathfinding детерминирован по состоянию мира.
