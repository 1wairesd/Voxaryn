## 2. Внешний аудит: что подтвердилось

### 2.1 [High] Фиксированный reach не учитывает быстрых мобов — **подтверждено, воспроизведено, исправлено**

- **Суть.** Радиус плана был follow range + 11. Запас 11 предполагал, что
  моб сдвигается за тик не больше 4 блоков по x/z. Скорость моба этим ничем
  не ограничена. Horizon к тому же загружает `Motion` из NBT без ванильного
  обнуления компонент больше 10; это отдельное расхождение с ванилью, вне
  Voxaryn.
- **Воспроизведение** (`tools/voxaryn/repro_fast_mover.py`). Два стада по
  100 коров; корова-«снаряд» с `Motion:[62,0,0]` за один тик долетает до
  стада B1, verify проверяет каждый тик.

  | Бинарник | параллельных | сверено | расхождений | откаты |
  |---|---:|---:|---:|---|
  | до исправления | 400/400 | 400 | **1** (`mob 406`: скорость — потерянный толчок между островами) | — |
  | после | 341/400 | 341 | **0** | `one-island` на 30 тиках со «снарядами» |

  Ошибка возможна и при ванильно допустимых скоростях (≤ 10 по оси). Пример:
  телёнок и родитель (`FollowParent`, 8 блоков) в соседних непересекающихся
  колонках сходятся до 16 блоков за тик при запасе 8.
- **Исправление** (`mobs/islands.rs`: `step_budget`, `reach_margin`,
  `exceeds_step`):
  - запас = 3 (боксы) + 2 × (наибольшая скорость любого моба по x/z на
    начало тика + 1.0); при обычных скоростях ≤ 3 блоков/тик он не меньше
    прежних 11;
  - после прохода каждый моб проверяется: сдвинулся ли он по x/z не дальше
    шага плана.

  Нарушение даёт ошибку в лог, проход выключается до конца процесса, а в
  verify-режиме берётся эталон. Тесты: `the_margin_grows_with_the_fastest_mob`.
- **Что осталось.** Прибавку скорости внутри тика (+1.0) доказать нельзя:
  толчки дают до 0.05 каждый. Нарушение **обнаруживается, но не
  предотвращается**: результат такого тика нельзя пересчитать без копии
  состояния. Во всех прогонах P1.1 тревога не сработала ни разу.

### 2.2 [Medium] `difference()` может упасть на UTF-8 — **подтверждено, исправлено**

- **Суть.** Отчёт о расхождении резал `Debug`-текст моба по сырым байтовым
  смещениям (`&sa[at-120..]`). Имя моба на кириллице (или любой не-ASCII
  символ рядом с отличием) → срез внутри символа → panic серверного потока.
  Затронут только путь, где расхождение уже найдено, но падение сервера хуже
  записи в лог.
- **Воспроизведение.** Юнит-тест `excerpts_cut_on_character_boundaries`
  (bin): старая формула на тексте из «ё» падает (`catch_unwind`), новая —
  нет.
- **Исправление.** `first_difference` + `excerpt` режут только по границам
  символов. Заодно исправлен второй мелкий дефект: если один текст был
  префиксом другого, место отличия называлось нулём.

### 2.3 [Medium] `VERIFY=N` не ловит расхождения между сверками — **подтверждено**

- **Суть.** Эталон считается от **текущего** состояния. Если тик без сверки
  разошёлся, расхождение переходит в состояние, и следующая сверка сравнивает
  только свой шаг от уже испорченного состояния. В P1 я утверждал, что
  расхождение «проявилось бы в следующей сверке». **Это неверно**
  (исправлено в p1-correctness §2). Повторяющийся дефект N-выборка ловит, как
  в негативном тесте; разовый — нет.
- **Что сделано.**
  - Описание `VERIFY` исправлено в коде и документах: N > 1 — выборка.
  - Полная сверка `VERIFY=1` выполнена на итоговом бинарнике: 6 сцен ×
    100 подряд тиков, 6 потоков, `shuffle:7` (`p11_verify_every.json`).
    Итог — **600 сверенных проходов, 0 расхождений**:
    - `herds_8x250`;
    - `species_land_8x250`, `species_water_8x250`;
    - `player_arena`;
    - `effects_breed_8x250`;
    - `mixedv_8x250`.
  - Отрицательный тест и воспроизведение #1 тоже шли с `VERIFY=1`.
- **Ограничение.** Полная сверка стоит ~2.4 с на тик при 2000 мобах
  (форматирование `Debug`). Поэтому длинные окна по-прежнему проверяются
  выборкой. Это записано как ограничение, а не как доказательство.

### 2.4 [Риск] Потеря изменений level RNG — **подтверждено по коду, исправлено**

- **Суть.** Если остров всё же тянул level random, страховка выключала
  проход, но `out.scratch` оставался в состоянии **до** прохода: вытяжки
  острова терялись, и level random этого тика отличался от
  последовательного.
- **Исправление.**
  - Ровно один тянувший остров → его копия и есть последовательный результат
    (все вытяжки из его мобов, в их порядке, из того же состояния): она
    принимается.
  - Два и больше → порядок восстановить нельзя: ошибка в лог, проход
    выключается, в verify-режиме берётся эталон.
- **Не воспроизведено во время игры.** Ни один проверенный вид не тянет level
  random, тревога не сработала ни в одном прогоне. Нужен был бы тестовый хук
  с подменой вида; его не делал.

> **P1.2.** §2.1 (движение) и §2.4 (level random) доработаны: граница шага
> теперь доказывается до прохода, общий RNG исключён архитектурно, а
> непроверенный результат не принимается (копия + последовательный пересчёт).
> См. [p12-correctness.md](p12-correctness.md).

### 2.5 Что осталось непроверенным

- Доказанная граница прибавки скорости внутри тика (§2.1): обнаруживается,
  но не предотвращается.
- Путь «≥ 2 острова тянули level random» во время игры (§2.4).
- Сцены с LAN-гостями.

## 4. Аудит новых видов

Для каждого вида проверены все чтения других мобов, доступ к level random,
записи вне себя и глобальное состояние (код: `mobs/aquatic.rs`,
`mobs/undead.rs`, `mobs/hostile.rs`, `mobs/nautilus.rs`, `mobs/goals.rs`,
`mobs/ai.rs`; level random доходит только до брейнов, `copper_golem` и

| Вид | Чтения других мобов | Level random | Вердикт |
|---|---|---|---|
| Кальмар, светящийся | только обидчик по id (`Seen.hurt_by`), толкание | нет | ✓ |
| Дельфин | тревога HurtByTarget (≤ follow range + 1, как у зомби), цель по id | нет | ✓ |
| Утопленник | как зомби: `nearby(follow range)`, тревога, цель | нет | ✓ |
| Коза | только толкание (брейн козы в Horizon не портирован) | нет | ✓; пересмотреть, если появится брейн |
| Наутилус | `nearby(16)`, Breed (партнёр по id → `held_mob`), цель | нет | ✓ |
| Скелет | `nearby(follow range)`, `AvoidEntity(6)` (дальше хранит **позицию**, не id), цель | нет | ✓ |
| Паук | `nearby`, `AvoidEntity(6)`, `LeapAtTarget` (цель) | нет | ✓ |
| Крипер | `AvoidEntity(6)`, `Swell` (цель); взрыв — событие после прохода | нет | ✓ |

Сопутствующая находка: `BreedGoal.canContinueToUse` держит партнёра по id
**без проверки дистанции**. В P1 такую пару могло разнести по островам —
латентный риск P1 для коров, свиней и овец. Сначала было правило «все
влюблённые одного вида — один остров». Оно сливало все загоны в один остров
(сцена размножения уходила в `dominant`), поэтому заменено точной связью
через `Goal::held_mob`.

## 6. Планирование: стоимость островов вместо «≥ 75 %»

Оценка стоимости реализована как диагностика (`islands::makespan`, поле
`est`). Это жадное расписание LPT по числу тикающих мобов на данное число
работников, тесты есть. Она совпадает с измеренным ускорением прохода против
`work` того же прогона (4.0 против 4.3 на 6 потоках, 1.70 против 1.70–1.88 на
неравных островах). Но она **завышает** реальный выигрыш на величину
раздувания работы (p1-overhead §2).

**Правило ≥ 75 % не заменено.** На всех измеренных сценах обе схемы
решают одинаково, воспроизводимого выигрыша нет. Различаться они будут при
1–2 работниках и 2–3 неравных островах. Таких сцен в наборе нет, и выигрыш
там меньше 1.3× даже в теории. Если замена понадобится: включать
параллельно при `est / раздувание(T) − (split+merge)/проход ≥ 1.2`.

Уменьшение консервативных откатов: проверено 9 видов (§4). Остров для
непроверенных видов («последовательная полоса») не сделан. Непроверенный моб
может читать **любого** моба (глобальные сканы), поэтому без аудита его
чтений полоса не доказуема. Reach-контракты не ослаблялись.
