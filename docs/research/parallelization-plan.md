# parallelization-plan.md — Обоснованный план многопоточного тика

> Фаза 1, задача 5. Варианты опираются на реально изученный код (`tick-architecture.md`)
> и анализ Pumpkin (`pumpkin-analysis.md`). На первом этапе игровой тик **не
> переписывается**; однопоточная реализация сохраняется как эталон. Этот документ —
> план, не реализация.

## 0. Отправная точка (из кода)

- Симуляция строго однопоточна: один `Game` владеет `&mut World` и всеми коллекциями
  сущностей; мутация блоков — через `with_level(|b, level, ticks| ...)`.
- Параллельны только фоновые задачи: `streaming.rs` (gen/light/mesh) и `net.rs`, общение
  через `mpsc` + `Arc`/`Mutex`/`Condvar`. Rayon/tokio в игровых крейтах нет.
- Порядок событий и RNG гарантированы единственностью `&mut`. Это сильная, но
  непараллелизуемая гарантия.
- Профилировщик фаз (`spans::time`) уже встроен в `tick_world` — можно измерять до/после.

Фундаментальный барьер для параллелизма: **всё изменяемое состояние за одним `&mut`**.
Любой параллельный вариант требует либо (а) выделить непересекающиеся множества работы
и дать каждому эксклюзивный доступ, либо (б) перевести состояние на разделяемые
примитивы (как Pumpkin — `Arc` + атомики), что есть полный передел модели данных.

## 1. Критерии оценки

Для каждого варианта: потенциал ускорения · стоимость синхронизации · сложность ·
риск нарушения порядка событий · влияние на детерминизм · совместимость с текущим
кодом · способ тестирования.

---

## Вариант A — Параллелизм внутри фаз, не меняя владение (data-parallel «read-mostly»)

**Идея.** Оставить `&mut Game` и последовательный каркас тика, но внутри одной фазы
распараллелить **чистые/почти-чистые** под-вычисления, результат которых затем
применяется последовательно. Классический «fork-join над снапшотом».

Кандидаты (по коду `tick_world`), где работа близка к read-only:
- планирование AI/путей: посчитать намерения мобов (`tick_creatures` → цели,
  пути) параллельно по снапшоту мира, затем применить движение последовательно;
- выбор случайных тиков по чанкам (`tick_chunk_random` в `tick_blocks`) — вычислить
  список позиций-кандидатов параллельно, применить эффекты последовательно;
- сбор `entity_inside`-боксов, отбор тикаемых сущностей.

**Как.** Собрать входные данные фазы в `Vec`, `rayon::par_iter().map(...)` по неизменяемому
снапшоту (`&World`), вернуть список «намерений/изменений», применить их детерминированно
в исходном порядке через существующий `with_level`.

| Критерий | Оценка |
|---|---|
| Потенциал ускорения | средний: ускоряет только «тяжёлую чистую часть» фазы; применение остаётся последовательным (закон Амдала) |
| Стоимость синхронизации | низкая: fork-join на границе фазы, без разделяемых локов |
| Сложность | низкая-средняя: не трогает модель владения |
| Риск порядка событий | низкий: применение изменений — в детерминированном порядке |
| Детерминизм | сохраняется, **если** параллельная часть чистая и RNG вынесен в последовательное применение (порядок draws как в vanilla) |
| Совместимость | высокая: аддитивно, однопоточный путь остаётся рядом |
| Тестирование | parity-харнессы затронутой фазы + сверка NBT до/после; spans показывают выигрыш |

**Главный риск:** в Horizon «чистых» фаз мало — тик сущностей и блоков активно мутирует
мир и дёргает RNG. Нужно аккуратно вычленять именно вычислительную часть (пути, выбор
целей, кандидаты тиков), иначе детерминизм ломается.

## Вариант B — Параллельный тик по регионам/измерениям (region/level sharding)

**Идея.** Использовать уже существующий своп уровней (`enter_level`, `Levels::parked`) и
расширить его до **параллельного** тика непересекающихся регионов. Сейчас `tick_server`
проходит измерения последовательно (`for dim in levels_to_tick()`). Поскольку уровни
разных измерений держат раздельное состояние, они — естественные непересекающиеся
домены. Дальше — дробление одного измерения на регионы (как `Region(RegionDomainId)` в
`pumpkin-scheduler`), с контролируемой доставкой кросс-региональных событий.

**Как (поэтапно).**
1. Шаг 1 (малый): тикать разные **измерения** параллельно. Требует снять единственность
   `&mut Game`: вынести per-level состояние из `Game` в самостоятельные владеемые объекты
   `Level`, тикаемые независимо. Это ломает нынешний `mem::swap`-подход.
2. Шаг 2 (большой): разбить измерение на регионы-воркеры с эксклюзивным владением чанками;
   кросс-региональные эффекты (redstone через границу, сущности на стыке) — через очередь
   owned-событий, применяемую на фиксированной фазе (модель доменов Pumpkin).

| Критерий | Оценка |
|---|---|
| Потенциал ускорения | высокий при многих активных регионах/игроках; на пустом мире ≈ 0 |
| Стоимость синхронизации | средняя-высокая: нужна дисциплина границ регионов и буфер кросс-событий |
| Сложность | **высокая**: ломает `Game`-владение и `mem::swap`-свопы уровней; большой передел |
| Риск порядка событий | высокий на границах регионов (redstone, толчки сущностей, порталы) — ровно то, что Pumpkin решает reach-анализом и fallback в `global` |
| Детерминизм | под угрозой: порядок применения кросс-региональных событий должен быть фиксирован; иначе расхождение с vanilla |
| Совместимость | низкая на шаге 2: затрагивает `game.rs`, `levels.rs`, модель `World` |
| Тестирование | `lan_e2e --server-thread` (порталы/уровни), parity, сверка детерминизма; очень дорого |

**Это целевая архитектура Voxaryn (README), но не первый шаг.** Нарушает ограничение
«не переписывать тик на первом этапе».

## Вариант C — Параллельный тик сущностей через reach-острова (портируем идею Pumpkin)

**Идея.** Воспроизвести концепцию Pumpkin: разбить сущности текущего тика на острова,
не пересекающиеся по reach (область чтения/записи), тикать острова параллельно, внутри
острова — в порядке списка. Результат эквивалентен последовательному тику.

**Как.** Для каждого моба/сущности посчитать `reach` (bbox движения + радиус толчков +
соседний блок-апдейт = длина redstone-сигнала + контактные блоки). Разрешить
пересечения в острова. Тикать `islands.par_iter()`. Консервативный fallback: сущности с
непредсказуемым reach (порталы, взрывы, глобальные эффекты) → один большой остров.

| Критерий | Оценка |
|---|---|
| Потенциал ускорения | высокий при многих рассредоточенных сущностях; низкий при скоплении (один большой остров) |
| Стоимость синхронизации | высокая: требует атомарного/разделяемого состояния сущностей (Pumpkin: `pos.load()`), fork-join на reach-анализ |
| Сложность | **очень высокая**: нынешние сущности — поля `Game` под `&mut`, не `Arc`+атомики; нужен передел хранения |
| Риск порядка событий | средний при корректном reach; **баг reach = тихий рассинхрон** |
| Детерминизм | сохраняется только при точном reach и фиксированном порядке внутри острова; требует обширной parity-проверки |
| Совместимость | низкая: меняет модель состояния сущностей |
| Тестирование | mob_ai, server_entities, сверка детерминизма; нужен reach-аудит |

**Это самый мощный, но и самый рискованный путь.** Прямой перенос кода Pumpkin запрещён
(GPLv3 vs MIT) — только идея, код заново.

## 3. Выбор: наименьший полезный прототип

**Прототип P0 — измерительный каркас + один параллельный «чистый» под-шаг (Вариант A,
минимальная версия).** Проверяемая гипотеза:

> **H0:** в типичной нагрузке существует фаза тика, чья тяжёлая часть *чисто
> вычислительна* и может быть вынесена в `rayon::par_iter` по снапшоту мира с
> последующим детерминированным применением — **без** изменения результата
> симуляции и **с** измеримым сокращением времени этой фазы.

Почему именно это:
- Не переписывает тик, не трогает владение `Game`, сохраняет однопоточный путь —
  соблюдает все ограничения фазы 1/2.
- Опирается на уже встроенный `spans::time` — выигрыш сразу виден в разбивке тика.
- Проверяет ключевое архитектурное допущение Voxaryn (можно ли вообще безопасно
  параллелить часть тика) малой кровью, прежде чем вкладываться в B/C.
- Даёт переиспользуемый fork-join-паттерн (снапшот → `par_iter` → детерминированное
  применение) для последующих вариантов.

### Конкретный первый кандидат-фаза
По `tick-architecture.md` наиболее перспективна **вычислительная часть pathfinding/AI**
(`tick_creatures` → расчёт путей) или **отбор random-tick кандидатов** в `tick_blocks`:
обе имеют тяжёлую чистую часть (поиск пути / выбор позиций) и отдельную фазу применения.
Точную фазу выбрать по данным профиля (S1/S2 из `benchmark-plan.md`), а не по догадке.

### Объём P0 (намеренно крошечный)
1. Добавить `rayon` только как dev/опциональную зависимость для прототипа (за feature-флагом,
   не в дефолтную сборку — чтобы не трогать production-путь).
2. Выбрать одну фазу по профилю; вынести её чистое вычисление в `par_iter` по `&World`.
3. Применение результатов — строго в исходном порядке через существующий путь.
4. Флаг включения параллелизма (env/feature), по умолчанию **выключен** → однопоточный
   эталон нетронут.

## 4. Критерии успеха P0

1. **Корректность (главное):** на фиксированном сценарии (seed 12345, скриптованные
   действия) итоговый NBT региона и сущностей **побитово совпадает** между однопоточным
   эталоном и прототипом (детерминизм не нарушен). Затронутые parity-харнессы зелёные
   (там, где доступны ресурсы/Python).
2. **Выигрыш:** доля целевой фазы в `spans`-разбивке тика сокращается на ≥ X% при
   нагрузке S1/S2 на ≥ 4 ядрах (конкретный X зафиксировать по baseline-профилю; заявлять
   только измеренное).
3. **Нет регресса:** на пустом/малонагруженном мире MSPT не растёт (fork-join не должен
   добавлять оверхед, когда работы мало — порог включения, как `MIN_PARALLEL_ENTITIES`
   в Pumpkin).
4. **Изоляция:** при выключенном флаге поведение и производительность идентичны текущим;
   `cargo fmt`/`clippy -D warnings`/тесты затронутых крейтов зелёные.
5. **Воспроизводимость:** отчёты baseline и proto сохранены в `benchmarks/` по протоколу
   §4 `benchmark-plan.md`, с ci95.

## 5. Чего P0 сознательно НЕ делает

- Не трогает `enter_level`/`mem::swap` (это Вариант B).
- Не переводит сущности на `Arc`+атомики (это Вариант C).
- Не меняет порядок измерений в `tick_server`.
- Не включает параллелизм по умолчанию.

Варианты B и C остаются долгосрочной целью (региональные домены — прямой путь к
заявленной в README архитектуре), но только после того, как P0 подтвердит, что безопасный
параллелизм части тика в Horizon в принципе достижим и измеримо полезен.
