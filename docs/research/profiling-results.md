# profiling-results.md — Исходная производительность игрового тика

> Фаза 1.5, задача 4. Все числа ниже — **реально измерены** на этой машине
> 2026-11-06 через собственный `/tick query` сервера (vanilla
> `ServerTickRateManager`) и разбор потиковых спанов `HORIZON_SPIKES`.
> Результаты разных условий не смешиваются. Где измерение неполно/недостоверно,
> это сказано явно.

**Важная платформенная оговорка:** `spans::thread_cpu()` возвращает `None` на
не-Unix (см. `crates/horizon-client/src/spans.rs`), поэтому на Windows `cpu_ms`
спана = его wall `ms`. **Разделение «считал / ждал (лок/GPU/ядро)» на Windows
недоступно.** Приведённые доли фаз — по wall-времени.

**Оговорка по разбору фаз:** `spans::describe()` показывает только спаны ≥ 0.5 мс.
Поэтому на лёгких сценариях (<0.5 мс суммарно) разбивка пуста, а на тяжёлых видны
только доминирующие фазы. Это свойство существующего инструмента, не отсутствие
активности в других фазах.

## 2. Результаты по сценариям (не смешивать)

Каждый сценарий — **свежий процесс сервера и свежая папка мира**. Сущности
создаются консольными командами (`summon`); для контроля числа отключён
`doMobSpawning`, кроме сценария 1.

| Сценарий | Сущностей | MSPT avg | P95 | P99 | TPS | Доминирующая фаза (wall) |
|---|---:|---:|---:|---:|---:|---|
| 1. Пустой мир | 21 (ambient) | **0.258** | 0.342 | 0.467 | 20.0 | все < 0.5 мс |
| 2. Умеренно сущностей | 221 | **0.40** | 0.575 | 0.808 | 20.0 | все < 0.5 мс (пик `tick_sculk_entities` 0.6) |
| 3. Высокая концентрация | 2021 | **2.117** | 2.692 | 3.158 | 20.0 | **`tick_mobs` 1.261 (~60%)**, `entity_portals` 0.557 |
| 4. Удалённые области (4×) | 1621 | **1.792** | 2.217 | 2.442 | 20.0 | **`tick_mobs` 1.082 (~60%)**, `entity_portals` 0.522 |
| 5. Redstone/механизмы | 21 | **0.583** | 0.833 | 1.0 | 20.0 | блок-фазы < 0.5 мс (см. §4) |

Все сценарии держат **20.0 TPS** (тик укладывается в 50 мс с огромным запасом).
Абсолютные значения малы, потому что это современный desktop CPU без игроков и без
экстремальной нагрузки — но **форма профиля уже видна**.

### Детализация фаз (sample = сколько потиковых строк дали спан ≥ 0.5 мс)

Сценарий 3 (2021 сущность), окно 60 с ≈ 1200 тиков:
- `tick_mobs`: среднее 1.261 мс, **1224 сэмпла** (≈ каждый тик) — главная статья.
- `entity_portals`: 0.557 мс, 193 сэмпла.
- `tick_sculk_entities`: 0.55 мс, 6 сэмплов (редко).

Сценарий 4 (1621 сущность, 4 кластера по ~400): `tick_mobs` 1.082 мс, 1225 сэмплов;
`entity_portals` 0.522 мс, 9 сэмплов.

**Вывод по профилю:** при любой заметной сущностной нагрузке доминирует
`tick_mobs` (внутри — `tick_creatures` → тики мобов, AI, pathfinding). Это ≈ 60%
тика при 1600–2000 сущностей и почти каждый тик превышает порог 0.5 мс. Остальные
фазы (блоки, блок-сущности, предметы) на этих сценариях остаются ниже 0.5 мс и не
выделяются.

## 3. Отдельный учёт прогрева, генерации чанков и сохранения

Исключены из окна измерения:
- **Старт до `Done`:** 5.6–6.1 с на сценарий (загрузка ресурсов ≈ 2.3 с + генерация
  спавна). Не входит в MSPT.
- **Прогрев:** 30 с после постройки сценария — спавн/генерация/расстановка сущностей
  устаканиваются до начала замера.
- **Автосохранение:** каждые 6000 тиков (5 мин) — окно 60 с его не захватывает.
- **Генерация чанков:** идёт на фоновых воркерах (`streaming.rs`), не на тик-потоке;
  в MSPT тик-потока не входит, но конкурирует за ядра (на этом 6-ядерном CPU запас есть).

## 4. Чего измерить не удалось / недостоверно (честно)

- **Сценарий 5 (redstone) недооценивает блок-тики.** Построенное поле
  (`fill redstone_wire` над `redstone_block`) зажглось статически и не создало
  устойчивых scheduled/random-тиков. MSPT 0.583 мс отражает в основном ambient-мир,
  не активную redstone-нагрузку. `tick_blocks`/`tick_scheduled` остались < 0.5 мс и
  не атрибутированы. Нужен сценарий с реальным осциллятором (observer-clock,
  поршневой/компараторный таймер), чтобы нагрузить блок-фазы. **Это ограничение
  сценария, не вывод об отсутствии стоимости.**
- **Нет разбиения `tick_mobs` на AI / pathfinding / физику.** Текущие спаны
  оборачивают фазы `tick_world`, но не под-шаги `tick_creatures`. Чтобы отделить
  pathfinding (A* `Finder::find`) от применения движения, нужна дополнительная
  инструментализация внутри `tick_creature_entities` (добавочные `spans::time`
  вокруг под-шагов) — на этом этапе не делалось (не меняем prod-код ради замеров).
- **Нет CPU-vs-wall на Windows** (`thread_cpu()` = None). Нельзя отличить «считал» от
  «ждал лок». Для сравнения стоимости синхронизации будущего параллелизма это
  придётся мерить на Linux/macOS или через внешний профайлер (ETW/VTune).
- **Нет P0.1% / длинных хвостов** — `/tick query` даёт только avg/P50/P95/P99 за
  последние 100 тиков. Для спайков нужен лог `HORIZON_SPIKES` с порогом.
- **Нет многопользовательской нагрузки.** Полноценный `server_bench.py` (боты
  walk/explore, сравнение с vanilla) не запускался: он Unix-ориентирован (`ps`,
  `ssh`). Числа выше — без игроков, сущности расставлены командами.

## 5. Как воспроизвести

```powershell
# окружение
$env:JAVA_HOME = "C:\Program Files\Eclipse Adoptium\jdk-25.0.5.8-hotspot"
$env:HORIZON_SERVER_JAR = "$env:TEMP\mc263server.jar"
# один сценарий
py -3 .local/tick_bench.py --scenario dense_entities --warmup 30 --seconds 60
# все пять (свежий сервер на каждый, свободный порт выбирается автоматически)
py -3 .local/tick_bench.py --scenario all
```

Отчёты пишутся в `.local/tick-bench/*.json` (не в Git). Сборка:
`cargo build --release -p horizon-client --bin horizon-client`.

## 6. Что это даёт для P0

Измерения однозначно указывают на **`tick_mobs` / `tick_creatures`** как первую
подсистему для распараллеливания: это доминирующая фаза под сущностной нагрузкой,
срабатывает почти каждый тик, и её тяжёлая часть (pathfinding) — read-mostly
(см. `tick-architecture.md` §9 и `parallel-candidates.md`). Подробный выбор,
зависимости и стоимость синхронизации — в `parallel-candidates.md`.
